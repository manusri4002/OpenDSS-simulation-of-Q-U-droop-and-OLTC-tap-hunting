# Q(U) Droop / OLTC Tap-Hunting Co-Simulation

Code scaffold for: *"Co-Simulation of Q(U) Droop Dead-Band and Response-Time
Effects on OLTC Tap Hunting Across Distribution Feeders with Different X/R
Ratios Under High PV Variability"*

## 1. Design decision: use OpenDSS's native controls, not a hand-rolled state machine

OpenDSS already ships with two objects that implement exactly the two control
loops in Section 2.1 of the paper, so instead of writing a custom Q(U) engine
and OLTC state machine in Python, we drive OpenDSS's own controllers and let
`opendssdirect` step through a QSTS (quasi-static time series) simulation:

| Paper concept                          | OpenDSS object                          | Key properties |
|-----------------------------------------|------------------------------------------|-----------------|
| Q(U) droop, dead-band width            | `InvControl` (`VOLTVAR` mode)            | `vvc_curve1` (the Q(U) curve — dead-band is the flat middle segment) |
| Q(U) response-time constant            | `InvControl`                             | `RateOfChangeMode=LPF`, `LPFTau=<seconds>` |
| PV reactive-power saturation/curtailment | `InvControl` / `PVSystem`              | read `kvar`, `kvarLimit`, compare dispatched vs requested Q |
| OLTC (substation regulator)            | `RegControl` on the substation transformer | `band` = LDC dead-band (%), `delay` = confirmation delay timer (s), `tapdelay` |
| Switched capacitor bank                | `CapControl`                             | `deadtime`, `delay`, `ONsetting`/`OFFsetting` |
| Feeder X/R class                       | Choice of test feeder                    | IEEE13 (low-X/R proxy, mostly UG-like short lines... see note below), IEEE34 (med), IEEE123 (varies) — **see Step 1**, you may need to hand-edit line X/R on one feeder to get a clean 3-way split |
| 1-second cloud-edge PV variability     | Custom `LoadShape` (`sinterval=1`) fed into `PVSystem.irradiance`/`Pmpp` scaling | generated by `pv_profile.py` |
| "taps/day" metric                       | Poll `RegControl`/transformer tap position every step, count changes | done in `cosim_engine.py` |

## 2. Prerequisites

```bash
pip install opendssdirect.py numpy pandas matplotlib scipy pyDOE2
```

Locate your local OpenDSS install's IEEE test feeders, typically:
- Windows: `C:\Program Files\OpenDSS\IEEETestCases\13Bus\IEEE13Nodeckt.dss`
- and sibling folders `34Bus\ieee34Mod1.dss`, `123Bus\IEEE123Master.dss`

Set these three paths in `config.py` (create from `config.py.example`).

### X/R caveat: read before running
IEEE13/34/123 are **not** pre-labeled by X/R class in the literature the way
your paper implies. Standard values are roughly:
- IEEE13: short, high-impedance overhead: moderate-high X/R
- IEEE34: long rural overhead feeder: **highest** X/R (most inductive per unit length)
- IEEE123: mixed OH/UG, more resistive laterals: tends **lower** X/R

So the mapping is likely **34-bus = high X/R, 13-bus = medium, 123-bus = low**,
opposite of numeric order — but this needs to be *verified*, not assumed.
`feeder_xr_check.py` (below) computes the average line X/R for each feeder
from its actual impedance data so you can assign classes empirically and
report the real numbers in Section 2.2, rather than asserting bus-count order.

## 3. File map

- `config.py.example` :— paths + global settings, copy to `config.py`
- `feeder_xr_check.py` :— computes average X/R per feeder, run this FIRST
- `pv_profile.py` :— 1-second cloud-edge irradiance generator
- `feeder_setup.py` :— loads a feeder, attaches PVSystems + InvControl, configures RegControl/CapControl
- `cosim_engine.py` :— QSTS loop: steps PV input, solves, logs taps/voltage/curtailment
- `run_single.py` :— runs ONE (feeder, dead-band, response-time) configuration end-to-end, sanity check
- `sweep.py` :— (next step, not yet written) Latin hypercube sweep over dead-band × response-time × feeder class
- `attribution.py` :— (next step) PV- vs load-driven tap decomposition per Bai et al. methodology

## 4. Suggested order of work

1. Run `feeder_xr_check.py` → confirms/assigns your 3 X/R classes with real numbers (fixes the paper's Section 2.2 claim).
2. Run `run_single.py` on one feeder/config → confirms the wiring (PV → InvControl → RegControl tap events) actually works and produces a plausible taps/day count.
3. Once that's solid, we build `sweep.py` (the actual factorial/LHS study behind Figures 1–2) and `attribution.py` (Figure 4, tap-wear decomposition).
